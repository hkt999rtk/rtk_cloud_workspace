# PKI consumer PVC plan for deployment environments

Status: **dev active; staging and production plan-only**. No new PVC is authorized by this document. The fixed Video Cloud consumer renderer was merged as Video Cloud PR #722 and selected in this workspace. Staging still requires its own protected Go/No-Go and a confirmed Linode quota before apply.

## Why three claims per environment

Device Root and Service Root certificates remain read-only ConfigMaps; service TLS material remains in Secrets. The consumer workloads still need writable state. Three claims preserve the only cross-container private-key boundary in the selected consumer design:

| Claim role | New claim | Initial request | Mount rule |
| --- | --- | ---: | --- |
| API trust state and controller identity | `video-cloud-api-pki-state` | 10 GiB | Two separate directories (`trust/`, `controller-identity/`) on one claim. Both are accessed by the same API container. |
| EMQX data and MQTT host identity | `mqtt-pki-private` | 10 GiB | Two separate directories (`emqx-data/`, `host-identity/`) on one claim. Mount only in the EMQX container. |
| MQTT writable trust state | `mqtt-pki-trust` | 10 GiB | Mount in the EMQX and `pkibroker` containers. The broker must not mount `mqtt-pki-private`. |

The previous five-claim staging renderer requested 45 GiB, but the dev `video-cloud-api-pki-trust` request of 5 GiB was provisioned as a 10 GiB Linode volume. Its real five-volume footprint was 50 GiB. Dev now uses three existing 10 GiB volumes: `video-cloud-api-pki-controller-identity`, `mqtt-pki-host-identity`, and `mqtt-pki-trust`. The source data was copied into isolated `trust/`, `controller-identity/`, `emqx-data/`, and `host-identity/` directories while consumers were stopped. On 2026-09-28 the two old dev PVCs, Retain PVs, and exact detached Linode volumes were deleted after the new consumers were Ready and no workload referenced them; Linode volume count fell from 33 to 31. The three-claim footprint is 30 GiB and three active services. Sharing the API state claim does not broaden a container boundary because the same API container already mounted both old claims. Sharing EMQX data and host identity similarly stays inside EMQX; keeping MQTT trust separate prevents the broker sidecar from reading host private material. Use separate subdirectories and validate permissions before the first workload starts. Do not use one PVC for all services or share a PVC between API and MQTT Pods.

## Tracked settings and environment differences

The deployment-environment files are `cloud_env/<environment>/pki-consumer-storage.json`. They contain the exact claim names, requests, storage class, and role-to-claim map. The read-only validator and renderer is `scripts/pki-consumer-storage-plan.py`.

| Environment | State | PVCs | Behavior |
| --- | --- | ---: | --- |
| dev | `active` | 3 | Three existing 10 GiB PVCs are mounted by Ready consumers; the two old source PVCs and volumes were retired. No new dev PVC is needed. |
| staging | `plan-only` | 3 | No claims currently exist. The three new names are reserved in the plan; any renderer output with five claims is rejected. |
| prod | `plan-only` | 3 | Planned layout only. No production resource is created or assumed to exist. |

Plan states record observed or intended layout; they are not resource-creation switches. The files contain no credentials, account quota, or cloud API token. Only a separately reviewed deployment operation may create resources. The account limit belongs in the environment-local operator account setting, sourced from Linode confirmation; do not place an invented value in Git.

## Dev migration and cleanup sequence

The dev plan retains the names of the two retired source PVCs, `video-cloud-api-pki-trust` and `mqtt-pki-data`, for audit and drift detection. The final role map uses three existing claims, so dev created **zero** new volumes. Read-only `deployment pki-storage-plan --environment dev --live` reports the three reused claims and verifies the two old claims are absent. The migration renderer refuses to create another migration Job from an `active` plan.

1. Run the scoped dev credential and workload checks. Capture the current two Deployment JSON documents, PVC/PV CSI IDs, images, resource versions, and rollback settings in owner-only local files. Confirm the final three claims are Bound and enough free space exists. Record a backup or retain both source claims until a verified restore path exists.
2. Render the two migration Jobs with `scripts/pki-consumer-dev-migration.py --render-job api|mqtt --image <exact-current-digest> --suffix <unique-session>`. Inspect every claim mount and command, then run Kubernetes client-side dry-run. Stop only `video-cloud-api-pki` and `mqtt-pki` with resource-version-guarded patches, and wait for their Pods to terminate. The ordinary API and MQTT workloads are separate and remain unchanged.
3. Apply the two reviewed Jobs. Each uses the current workload image, has no service-account token, reads one old source claim, writes to one existing target claim, copies the original identity directory into its new private subdirectory, and compares the copy against the source. MQTT `identity/` must be mode 0700 and every copied identity regular file mode 0600; set `fsGroupChangePolicy: OnRootMismatch` so Kubernetes does not widen those permissions on mount. Retain successful Job logs and wait for complete. On failure, do not switch mounts; restore the two Deployments to their recorded replica count and investigate.
4. Fetch fresh stopped Deployment JSON, then render guarded patches with `scripts/pki-consumer-dev-migration.py --render-patch api|mqtt --deployment-json <fresh-json>`. The patches test resourceVersion, stopped replicas, and the old claim names, add the reviewed `subPath` mounts, and return replicas to one. Apply each patch once; wait for both new Pods to be Ready. Verify root/trust and private identity files are present, test API device mTLS, MQTT PKI admission, renewal and persistence, and inspect errors. Keep the original Deployments and source claims available for rollback until these checks pass.
5. Delete the two completed migration Jobs and Pods. Run `deployment pki-storage-plan --environment dev --cleanup-audit`; it must confirm both new consumers are Ready on the exact three-claim layout and neither old source PVC is referenced by a Pod or workload template. Recheck the old PVC→PV→Linode volume IDs immediately before deletion. After a reviewed backup/rollback checkpoint, delete only those two old PVCs, their Retain PV objects, and their matching detached Linode volumes. `Retain` means PVC deletion by itself does **not** release the billed volume. Verify the account-wide volume count fell by two and rerun the live cleanup audit. Do not include the independent `openbao-recovery-20260818-1948` volume; its recovery ownership is still unproven.

No script above performs live mutation automatically. The reviewed operator commands apply the Jobs, guarded patches and final deletions in separate steps so a failed check cannot silently continue to destructive cleanup.

## Render, qualify, deploy, and verify

1. Validate each tracked plan with `go run ./scripts/go/rtk-cloud -- deployment pki-storage-plan --environment NAME`. `deployment plan` also prints the selected PKI storage summary. Add `--live` to compare claims with the selected environment's kubeconfig and, when any volume is new, query the Linode account-wide active-service count and compare the projection with the confirmed environment-local limit. A mismatch, unbound claim, or over-limit projection fails. Dev lists the two exact retired legacy sources and requires them to be absent in `active` state. The command never creates a resource.
2. The fixed Video Cloud staging renderer requires `--storage-plan cloud_env/staging/pki-consumer-storage.json`, maps the five logical roles to the three claims and subdirectories, and rejects the old five-claim layout. PR #722 passed required CI and was merged; verify the final rendered Pod mounts and claim list together before staging apply. Dev's migration is complete. Production will require its own environment-specific consumer render and protected review.
3. The dedicated `deployment pki-storage-plan --live` check includes the exact `NEW` claim count in its account-wide projection across instances, volumes, and NodeBalancers. Run it in addition to the ordinary provider plan, which does not apply this opt-in overlay. After dev cleanup on 2026-09-28, the account had 11 instances, 31 volumes, and no NodeBalancers: **42 active services**. A three-new-volume staging projection is **at least 45**. Linode support has confirmed only a limit of 20 so far. The no-growth exception does not apply. Obtain a confirmed limit sufficient for the current exact projection or deliberately retire separately verified resources before proceeding. Recheck immediately before mutation; no stale count or guessed quota is acceptable.
4. Render review-only manifests with `go run ./scripts/go/rtk-cloud -- deployment pki-storage-plan --environment staging --render > /protected/pki-pvcs.json`. Review namespace, claim names, Retain storage class, access mode and sizes. Run `kubectl --dry-run=client -f /protected/pki-pvcs.json -o name` with the verified staging kubeconfig. Use the protected-environment credential, PKI, image and migration Go/No-Go checks. No PVC is created by rendering or dry-run.
5. After the same selected release passes Go/No-Go, apply only the reviewed PVC manifest with the selected environment's kubeconfig. Wait for all three claims to be `Bound`, record CSI volume IDs and actual provisioned sizes, and confirm no unexpected fourth claim. Mount the reviewed consumer manifest, verify private-key permissions and container isolation, then complete Device Root bootstrap and end-to-end trust checks. Production repeats this with its own identity, quota, backups and approval gates; it never reuses staging PVCs or private state.
6. Rollback stops or restores consumers without deleting retained claims. PVC/volume deletion is a separate inventory, backup and retention decision; a failed rollout is not cleanup authorization. Regular drift review compares the tracked claim list, current PVCs, PV CSI IDs, and Pod mounts. Unreferenced claims are candidates for review, not automatic deletion.

Until the exact three-claim manifest is verified against its consumer mounts and the dedicated live capacity check passes, `plan-only` environments remain **NO-GO** for PKI consumer PVC creation. The latest staging projection is 45 against a confirmed limit of 20, so staging remains NO-GO even with the reduced layout.
