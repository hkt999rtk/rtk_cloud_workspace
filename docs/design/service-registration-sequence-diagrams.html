RTK Cloud · service registration

Register a service capability. Grant it to a Product. Then a device may use it.

MQTT is the required foundation; Shadow, WebRTC, and video storage are pluggable services. On a new deployment, a short-lived bootstrap X.509 leaf provisions the initial internal identities, then is revoked after verified installation. Platform Server is authoritative for the service catalog and Product grants. Factory writes only the fixed authorization into the device token, and each runtime validates it locally.

01 / CONTROL PLANEService capability registration and Product grants

This path establishes which services are selectable and which Product may use them. Service registration verifies the mTLS identity and manifest; it never directly grants a device any entitlement.

Platform authorityIt verifies service identity, stores versioned manifests, publishes a tenant/environment-scoped catalog, and persists Product grants.
Service authorityA runtime may declare options and dependencies only for its own service ID; it cannot register capability for another service.
Activation is not registrationAn optional service can start suspended. Its registered option still needs platform activation and a Product grant.

02 / DATA PLANEToken issuance and local runtime enforcement

This path establishes what the device may call now. The runtime does not look up the registry for every request; each service validates the Platform-signed token's option, revision, and device scope locally.

The token is an authorization snapshotFactory cannot expand a grant from request content. It signs only Platform-resolved effective options and the exact grant revision.
Every runtime enforces locallyMQTT and each optional runtime validate the signature, issuer/audience/lifetime, tenant/device scope, option, and revision.
The result is deterministicA device carrying only mqtt may connect to MQTT; Shadow, WebRTC, and video-storage requests without their matching option are denied.
